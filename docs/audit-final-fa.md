# ممیزی نهایی — وضعیت واقعی هر ۱۷ مورد

این سند نتیجه یک **بررسی برنامه‌ای** است، نه گزارش از روی حافظه. برای هر ادعا
یک بررسی خودکار روی کد اجرا شد و نتیجه PASS/FAIL ثبت گردید.

## روش کار

ابتدا اسکریپتی نوشتم که ~۱۱۰ ادعای فهرست شما را مستقیم در کد بررسی می‌کند
(وجود مدل، endpoint، کامپوننت، تست). سپس **هر PASS مشکوک را دستی بازبینی کردم**
— که کار درستی بود، چون grep در هر دو جهت دروغ می‌گوید.

**نمونه‌ی مهم:** «Export گزارش مالی» در اجرای اول PASS گرفت. علتش این بود که
grep دنبال `export` می‌گشت و به `export default function Finance()` رسیده بود.
صفحه Finance در واقع **هیچ قابلیت خروجی نداشت**. اگر فقط به اسکریپت اعتماد
می‌کردم، این مورد ناقص می‌ماند.

### بدترین دسته: داده‌ای که ذخیره می‌شد ولی دیده نمی‌شد

سه مورد از این‌ها الگوی یکسانی داشتند و از دید یک بررسی سطحی «انجام‌شده»
به نظر می‌رسیدند:

1. **دلیل رد آگهی** — بک‌اند آن را در `rejection_reason` می‌نوشت، سریالایزر
   برمی‌گرداند، و پنل مدیریت نمایش می‌داد. اما **غرفه‌دار** — تنها کسی که به آن
   نیاز داشت — هیچ‌جا آن را نمی‌دید. کارت آگهی در پروفایل فقط یک برچسب وضعیت
   داشت. یعنی فروشنده می‌فهمید «رد شد» ولی نه «چرا».
2. **هایلایت** — مدل، سریالایزر، ViewSet با CRUD کامل و تست، همه موجود. ولی هیچ
   دکمه‌ای در استودیو برای ساختنش نبود.
3. **تصویر غرفه** — `avatar` و `cover` در مدل و سریالایزر بودند، اما endpoint
   فقط JSON می‌پذیرفت و فرمی برای آپلود وجود نداشت.

این نوع نقص خطرناک است چون در تست‌های API سبز می‌شود.

## نتیجه اجرای دوم: ۱۵/۱۵ PASS

همه موارد بالا رفع شدند:

### دلیل رد، حالا برای غرفه‌دار

کارت آگهی ردشده در `/profile?tab=seller` با حاشیه قرمز، متن دلیل و این توضیح
نمایش داده می‌شود که «پس از اصلاح، آگهی دوباره برای بررسی ارسال می‌شود». تست
`SellerRejectionVisibilityTests` کل چرخه را پوشش می‌دهد: رد با دلیل → دیدن دلیل
توسط فروشنده → ویرایش → پاک شدن دلیل و بازگشت به صف بررسی.

### دفتر مالی، حالا واقعاً قابل استفاده

| قابلیت | جزئیات |
|---|---|
| شناسه تراکنش | `GKF-00000123` — قابل استناد در تیکت پشتیبانی |
| کد سفارش | روی هر ردیف |
| فیلتر | وضعیت، نوع رویداد، بازه تاریخ، جستجوی متنی |
| صفحه‌بندی | ۲۵ ردیف در هر صفحه |
| خروجی CSV | با BOM و نام فایل استاندارد |

دو تصمیم که ارزش توضیح دارند:

**BOM در CSV:** بدون `\ufeff` ابتدای فایل، Excel روی ویندوز متن فارسی را
mojibake نشان می‌دهد. برای مخاطبی که احتمالاً همان Excel را باز می‌کند، خروجی
بدون BOM عملاً بی‌فایده است.

**نام فایل RFC 5987:** نام فارسی باعث می‌شد هدر `Content-Disposition` به base64
تبدیل شود (`=?utf-8?b?...`) که بعضی مرورگرها عیناً ذخیره می‌کنند. حالا یک نام
ASCII به‌علاوه نسخه UTF-8 فرستاده می‌شود.

**موجودی‌ها هنگام فیلتر تغییر نمی‌کنند** — عمداً روی کل دفتر محاسبه می‌شوند. اگر
فیلتر روی موجودی هم اثر می‌گذاشت، فروشنده فکر می‌کرد موجودی قابل تسویه‌اش عوض
شده. این نوع ابهام در صفحه مالی قابل قبول نیست. تست دارد.

### ترجمه خطاها

سرور همیشه فارسی جواب می‌دهد، ولی هر خطا یک `code` پایدار دارد. **همان code
ترجمه می‌شود، نه متن.** پس تغییر زبان رابط، متن خطا را هم عوض می‌کند بدون اینکه
بک‌اند نیاز به مذاکره locale داشته باشد.

پیام‌های سطح‌فیلدی (`fields`) عمداً ترجمه **نمی‌شوند**: آن‌ها مقادیر مشخص دارند
(«حداقل سفارش ۵۰ کیلوگرم است») و ترجمه عمومی این جزئیات را از بین می‌برد.

### مانیتورینگ Rate Limit

هر درخواست بلاک‌شده در logger اختصاصی `garinkood.throttle` با scope، IP، مسیر و
شناسه کاربر ثبت می‌شود. `LOGGING` در settings پیکربندی شد تا یک سیستم مانیتورینگ
بتواند روی جهش تعداد بلاک‌ها هشدار بدهد — که یا نشانه حمله است یا نشانه اینکه
سقف را خیلی تنگ گذاشته‌ایم.

## آنچه هنوز انجام نشده — و چرا

این‌ها را آگاهانه انجام ندادم چون به تصمیم شما وابسته‌اند، نه به زمان:

### ۱. تسویه واقعی و برداشت وجه فروشنده
زیرساخت کامل است: دفتر مالی، دوره hold هفت‌روزه، وضعیت `available`. اما «واریز
به حساب فروشنده» نیازمند انتخاب سرویس تسویه (پایا/ساتنا، یا API بانکی) و
قرارداد حقوقی است. کد را برای اتصال آماده گذاشته‌ام ولی پیاده‌سازی بدون آن
تصمیم، حدس زدن است.

### ۲. اجرای واقعی Playwright و Lighthouse
باینری مرورگر در sandbox دانلود نمی‌شود (شبکه محدود است — هم `playwright
install` و هم `apt-get` برای وابستگی‌ها شکست می‌خورند). ۶۲۴ تست نوشته و
پیکربندی شده‌اند و `--list` می‌شوند، اما **اولین اجرای واقعی‌شان در CI خواهد
بود**. انتظار داشته باشید چند selector نیاز به تنظیم داشته باشد — این طبیعی است
و به معنی خراب بودن کد نیست.

### ۳. فعال‌سازی CI
پوش به `.github/workflows/` توسط GitHub رد می‌شود چون App دسترسی `workflows`
ندارد. فایل‌ها در `ci/workflows/` هستند با راهنمای دو-دستوری فعال‌سازی در
`ci/README.md`. **تا زمانی که این کار انجام نشود، هیچ‌کدام از تست‌های مرورگر
اجرا نمی‌شوند.**

### ۴. موتور جستجوی تصویری
صف آپلود و مدل `VisualSearchRequest` آماده است؛ مدل بینایی ماشین وصل نشده.

### ۵. Sentry / مانیتورینگ خارجی
لاگ ساختاریافته آماده شد، ولی اتصال به سرویس نیازمند DSN و تصمیم درباره
ارائه‌دهنده است.
