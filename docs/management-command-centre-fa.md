# مرکز مدیریت گرین کود

## مسیر

```text
/management
```

این مسیر فقط برای کاربران Django با `is_staff=True` باز می‌شود. مالک یا سوپریوزر می‌تواند نقش‌ها را مدیریت کند.

## نقش‌های آماده

برای ساخت یا به‌روزرسانی نقش‌ها:

```bash
cd garinkood
python manage.py bootstrap_management_roles
```

| نقش | دسترسی اصلی |
|---|---|
| عملیات | سفارش‌ها، سبد، محصول و کوپن |
| مالی | سفارش، پرداخت، ledger، کیف پول، کوپن و affiliate conversion |
| بازار و غرفه | غرفه، آگهی، پست/استوری و شکایت غرفه |
| پشتیبانی | درخواست خدمت، خرید محصول کشاورز، feedback، شکایت و کامنت |
| محتوا | کامنت، پست/استوری، آگهی و اطلاعات محصول |
| انبار | محصول، موجودی و سفارش |

## اصل کمترین دسترسی

- مدیر مالی نباید بدون نیاز، اجازه حذف محصول یا moderation محتوا داشته باشد.
- مدیر محتوا نباید payout یا تأیید پرداخت انجام دهد.
- فقط owner/superuser می‌تواند نقش‌ها و فعال/غیرفعال‌بودن کارمندان را تغییر دهد.
- هیچ token، رمز عبور یا credential پرداختی نباید در پنل یا Git ذخیره شود.

## بخش‌های فعلی داشبورد

- KPI فروش پرداخت‌شده
- سفارش‌های در انتظار بررسی
- شکایت‌های باز
- پست/استوری و آگهی در انتظار بررسی
- محصولات با موجودی کم
- تعداد غرفه‌های تأییدشده و affiliateهای فعال
- آخرین سفارش‌ها و action تأیید پرداخت
- صدور پاداش خرید بعدی هنگام تأیید پرداخت
- مدیریت نقش کارمندان برای owner
- audit log اقدامات مدیریتی
- سلامت و ظرفیت: توان اندازه‌گیری‌شدهٔ سرور، حاضران لحظه‌ای، صف ورودی و لاگ خطاها

## Audit Log

اعمال زیر در `AdminAuditLog` ثبت می‌شوند:

- تغییر نقش کارمند
- تأیید پرداخت سفارش از مرکز مدیریت
- moderation کامنت، پست و آگهی از API مدیریت

تغییرهای مستقیم Django Admin در حال حاضر از امکانات استاندارد Admin Log استفاده می‌کنند؛ برای audit یکپارچهٔ production می‌توان signal یا middleware مخصوص اضافه کرد.

## تب «سلامت و ظرفیت»

این تب سه سؤال را جواب می‌دهد و هیچ‌کدام را حدس نمی‌زند:

| پرسش | منبع پاسخ |
|---|---|
| سایت چقدر توان دارد؟ | `CapacitySettings` + اندازه‌گیری زنده از `/proc` و cgroup |
| چند نفر داخل‌اند؟ | جدول `PresenceBeat` (ردّ درخواست‌های واقعی) |
| چه چیزی خراب شد؟ | `SystemLogEntry` — هم خطای خودکار سمت سرور، هم گزارشی که کاربر از صفحه فرستاده |

### عدد ظرفیت

در حالت خودکار، سقف از کوچک‌ترِ «توان پردازنده» و «توان حافظه» می‌آید:

```text
پایه = min(هسته‌ها × کاربر_به_ازای_هر_هسته، گیگابایتِ_قابل_استفاده × کاربر_به_ازای_هر_گیگ)
سقف  = پایه × ضریب اطمینان            (کف امن: ۱۰ نفر)
```

- «گیگابایت قابل استفاده» کوچک‌ترِ `MemAvailable` و سقف کانتینر (`memory.max` یا `memory.limit_in_bytes`) است؛
  پس روی سرور اشتراکی، عدد داکر ملاک است نه عدد میزبان.
- اگر بار یک‌دقیقه‌ای هر هسته از آستانه رد شود، سقف *کم* می‌شود و علت در همان جملهٔ توضیح نوشته می‌شود.
- پردازنده گرافیکی فقط وقتی نمایش داده می‌شود که درایور واقعاً جواب بدهد؛ «۰» یعنی هیچ، نه «خالی است».
  GPU در *محاسبه* سقف نقشی ندارد (بار این سایت حافظه و CPU است، نه رندر) و فقط برای دیدن وضعیت سرور
  نشان داده می‌شود؛ اگر روزی بار GPU-محوری روی این ماشین بیاید، وزنش باید آگاهانه اضافه شود.

جملهٔ «چطور به این عدد رسیده‌ایم» زیر کارت‌ها همان متنی است که در جدول `ResourceSample` ذخیره می‌شود؛
پس تاریخچهٔ تصمیم هم قابل خواندن است، نه فقط عدد امروز.

### صف ورودی

کلید `queue_enabled` **پیش‌فرض خاموش** است. تا روشن نشده باشد، حتی اگر ظرفیت پر شده باشد هیچ کاربری
معطل نمی‌شود؛ پنل فقط فشار را نشان می‌دهد. بعد از روشن‌کردن:

- صفحهٔ درخواستی کاربر با یک صفحهٔ انتظارِ سبک جایگزین می‌شود که خودش هر ۱۵ ثانیه تازه می‌شود؛
  کاربر به هیچ آدرسی ریدایرکت نمی‌شود و نشانی‌اش گم نمی‌شود.
- درخواست‌های `API` با `503` و `Retry-After` جواب می‌گیرند؛ اپلیکیشن به‌جای انبوه پیام خطا،
  صفحهٔ «شما نفر … هستید» را نشان می‌دهد.
- `POST` هرگز در در نگه داشته نمی‌شود — ثبت سفارش نباید در صف گم شود.
- `/admin/`، مدیا، استاتیک، `health` و `metrics` همیشه بازند؛ حتی اگر سایت قفل شده باشد.
- کارمندان (در حالت پیش‌فرض) از صف رد می‌شوند تا کسی که باید سایت را درست کند، بیرون نماند.
- بعد از «سقف صبر» (`queue_max_minutes`) کاربر وارد می‌شود، حتی اگر سالن هنوز پر باشد.

### لاگ سیستم

- فقط پاسخ‌های `۵۰۰` و بالاتر ثبت می‌شوند (به‌علاوهٔ `۴۲۹` به‌عنوان اطلاع). `۴۰۴`ها وارد دفترچه نمی‌شوند.
- هر خطا یک *گروه* با شمارنده است؛ همان باگ در هر صفحه «۴٬۲۰۹ بار» نوشته می‌شود، نه چهارهزار ردیف.
- «برطرف شد» یعنی برچسب، نه حذف. اگر همان خطا دوباره بیاید، ردیف خودش دوباره باز می‌شود.
- بدنهٔ درخواست پیش از ذخیره پاک‌سازی می‌شود: رمز، توکن، کوکی، شمارهٔ کارت و CVV هرگز نوشته نمی‌شوند.
- دکمهٔ «اینجا خطا داد» در صفحهٔ خرابیِ اپ، همان گزارش را در همین لیست ثبت می‌کند؛ اگر کاربر متنی
  بنویسد، یک پیام در صندوق بازخورد هم ساخته می‌شود.

### دسترسی‌ها

| endpoint | چه‌کسی |
|---|---|
| `GET /api/ops/health/` | فقط staff (یا `OPERATIONS_TOKEN`)؛ بقیه `404` می‌گیرند |
| `GET /api/ops/logs/`، `POST /api/ops/logs/<id>/resolve/` | فقط staff |
| `GET /api/ops/admission/` | همه — فقط جای خودِ کاربر در صف را می‌گوید |
| `POST /api/system/report/` | همه، با سقف ۱۰ گزارش در ساعت |
| `GET /api/management/users/?online=1` | staff؛ لیست حاضران و بی‌سروصداهایی |

`404` برای غیرمسئولان عمدی است: «این پنل وجود دارد و قفل است» خودش اطلاعاتی است که به مهاجم داده نمی‌شود.
